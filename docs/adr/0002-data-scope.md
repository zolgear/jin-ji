# ADR-0002: 扱うデータの範囲と、システムの位置づけ

- ステータス: **承認**
- 日付: 2026-10-18
- 関連: [ADR-0001](0001-language-and-runtime.md)、[ADR-0012（提案）](0012-workplace-and-seat-data.md)（建物・階・座席）、[アーキテクチャ概要](../architecture/overview.md)、[建物・フロアモードの仕様](../design/building-floor-mode.md)、[ADR-0013（提案）](0013-field-managed-changes.md)（現場の直接登録。決定 1 の見直し）

## 決定

1. **jin-ji は人事情報の正（System of Record）ではない。** 正は既存の人事パッケージ。jin-ji はその下流で、人事パッケージと社内システム群をつなぐ**中間パイプ**であり、DX・AX の基盤となる。人事パッケージへは書き戻さない。
2. **一般通念で全社内に公開しても問題がない情報だけを保持する。** それ以外の項目は、取り込みの時点で捨て、DB に列を作らない。マイナンバーや履歴書レベルの個人情報は扱わない（例: 年齢は保持しないが、入社年月日は保持する。性別は保持しない）。
3. アクセス権の設定機能は持つ。ただしその目的は「機微情報を守る」ことではなく、次の 3 つである。
   - 全社公開を既定として、項目・組織・個人の単位で**公開範囲を狭める**。公開範囲は組織のルール（ポリシー）として決め、本人が自分の公開範囲を変える機能は持たない
   - 社内システムや AI エージェントなど、**利用者ごとに渡す項目を最小にする**
   - 未来日付の異動（内示）を**発令日まで秘匿する**
4. 休職・休業は**理由を持たないアカウントの一時停止**として扱う（下記）。
5. 拠点を人と組織に持たせ、リモートワークは**有無だけ**を扱う。シフトなどの勤務形態は対象外（下記）。
6. 社内システムへの変更の通知（Webhook）の本文は**種別と ID だけ**にし、値は受け手が自分のトークンで API から取り直す（下記）。
7. **人の決まった席・持ち場（固定席・工場の持ち場・副の席。有効期間付き）を、社内の座席表と同じ水準の情報として保持する。** 当日の所在・座席予約・フリーアドレスは保持しない（人事の範疇を超える施設管理で、連携先の範疇。下記）。

## 背景

人事情報を AI エージェントや社内システムへ安全に配るには、配る情報そのものの機微度を下げるのが最も確実である。機微情報を持ったうえで機密区分で守る設計は、認可の段階が増え、漏洩時の被害も大きく、LLM へ渡すときの障壁も高い。jin-ji の目的（人事情報の AI Ready 化）には、機微情報を最初から持たない方が合う。

## 保持する項目

| 分類 | 項目 | 備考 |
| --- | --- | --- |
| 識別 | jin-ji ID、社員番号、外部 ID の対応（人事パッケージ、Entra ID 等） | |
| 氏名 | **業務上の氏名**（通称・旧姓使用を含む）、フリガナ、ローマ字表記、表示名 | 戸籍上の氏名は保持しない（通称と異なる場合） |
| 所属 | 法人、組織、主務/兼務、役職、出向・出向受入の区別 | |
| 在籍 | 入社年月日、退職年月日、在籍状態（在籍/退職）、**アカウント状態（有効/一時停止）** | 一時停止は理由を持たない（下記） |
| 業務連絡先 | 社用メール、内線、社用携帯 | |
| 拠点 | 拠点（コード・名称・種別・所在地〔事業所の住所〕・法人・有効期間）、組織の拠点、人の拠点（既定は所属組織〔主務〕の拠点。人ごとに上書き可）、**リモートワークの有無** | リモートワークは有無だけ（下記） |
| 席の割り当て | 建物・階・配置図（外形・ゾーン・席の置き場所）、人の決まった席・持ち場（固定席・持ち場・副の席。有効期間付き） | 下の「席の割り当て」。当日の所在・座席予約は持たない |
| その他 | 雇用区分（正社員・契約・嘱託・派遣・出向受入など）、職種、顔写真 | 顔写真は保持してよい項目だが、取り込み・配信は未実装（[概要 §7.2](../architecture/overview.md#72-rest-api-の実装の規則)） |
| 組織 | 組織名・略称・コード・段（階層は法人ごとに設定可能）・上位組織・組織長・拠点・有効期間 | |
| 発令 | 異動・役職の任免・入退社・兼務・出向・一時停止の発令 | 給与等級・給与に関わる部分は取り込まない |

役職は保持し、給与等級は jin-ji の管轄外として保持しない。雇用区分は全社公開の項目として保持する。

## 保持しない項目

マイナンバー、生年月日・年齢、性別、住所・私用連絡先、家族・扶養、給与・賞与・給与等級、評価、健康情報・休職や休業の理由・障害、国籍、学歴・職歴（履歴書情報）、戸籍上の氏名（通称と異なる場合）、当日の所在（今日どこにいるか）・座席予約・フリーアドレスの日々の席、チェックイン（実際に座った時刻）・入退館・IC カード・PC のログオン・位置の測位の記録、在宅・出張・外出・休暇などの日々の場所や理由の区分、労働時間（勤怠）、健康・障害を推測させる席の属性（車椅子対応など）。

## 守り方

- **列を作らない**: 保持しない項目は、DB のスキーマに存在させない
- **取り込みの入口で捨てる**: 人事パッケージのエクスポートや Entra ID からの取り込みは、項目の許可リストで絞ってから保存する。生データ（staging）にも許可リスト外の項目は残さない
- **混入を検知する**: 自由記述の項目に、生年月日や住所らしき値が入っていないかを取り込み時に検査し、警告する
- **項目カタログをテストで守る**: 全テーブルの列が、上の表のどこかに分類されていること（`db/field-catalog.json`）をテストで確かめる。分類のない列を追加するとテストが失敗する。認証・監査など jin-ji の運用のための列は、上の表とは別の分類として同じカタログに載せる

## 注意が要る項目

| 項目 | 懸念 | 扱い |
| --- | --- | --- |
| 氏名の履歴 | 旧姓から新姓への変化は、婚姻・離婚を推測させる | 名寄せと過去データの照合に必要なので保持する。ただし参照は人事管理者に限り、一般の API・MCP では現在の氏名だけを返す |
| 顔写真 | 本人の意向が分かれる | 公開範囲は組織のルール（ポリシー）で決める。個人の裁量にはしない |
| 退職者 | 退職後も在籍者と同じように公開し続ける理由はない | 退職後の一定期間で一般公開をやめ、保持期限を過ぎたら匿名化する |

## 休職・休業の扱い

休職・産休・育休・介護休業・長期の療養などは、**アカウントの一時停止**として扱い、理由は保持しない。

- 理由ごとの区別を持たないので、一時停止から休職理由を推測されにくい。様々な事情を一つの状態で吸収できる
- 一時停止の開始日・終了予定日は有効期間として持つ。人事パッケージの休職情報は、取り込み時に「一時停止」へ変換し、理由は捨てる
- 社内システムには「一時停止中」という状態だけを配信する（例: Entra ID のサインイン停止、勤怠システムの打刻対象外）
- 一時停止中でも、組織図上の所属は維持する

## 拠点とリモートワーク

- 拠点は組織と人の両方に持たせる。人の拠点の既定は所属組織（主務）の拠点で、異なる場合だけ人ごとに持つ。自由記述の「勤務地」は持たず、拠点で表す
- 拠点の所在地は事業所の住所（会社の情報）であり、個人の住所ではない
- リモートワークは「対象か否か」だけを持つ。理由（育児・介護・健康など）・頻度・曜日・シフト・在宅の場所は持たない。休職を理由なしの一時停止で扱うのと同じ考え方で、有無から事情を推測されにくくする
- ビューでは、拠点ごと・リモートワークの対象者ごとにまとめて表示できる。公開範囲は他の項目と同じく組織のルール（ポリシー）で狭められる
- 実装の規則は [概要 §4.7](../architecture/overview.md#47-拠点とリモートワーク)

## 席の割り当て

- 建物・階・簡易フロアマップ（外形・ゾーン・席の置き場所）と、人の決まった席・持ち場（固定席・工場の持ち場・兼務先などの副の席）を有効期間付きで持つ。社内に掲示される座席表と同じ水準の情報とみなす。扱いは [ADR-0012](0012-workplace-and-seat-data.md)、仕様は [建物・フロアモード](../design/building-floor-mode.md)
- 項目は「階・エリア（`workplace`）」と「席（`seat`）」に分け、ポリシーで別々に狭められる。将来の割り当て（席替えの予定）は内示と同じく発令日まで秘匿する
- 工場の持ち場は人の割り当てだけで、シフト・勤務帯（誰がいつ入るか）は持たない
- 当日の所在・座席予約・フリーアドレス（組織のホームエリア・自由席）は持たない。人事の範疇を超える施設管理で、連携先の範疇である。所在を画面に出したい導入先には、jin-ji が保持せずに外部の提供を注入して表示する拡張点だけを用意する。人事管理者を含め、所在だけは全員を一覧できる立場を作らない（リアルタイムの所在は連携先の範疇。[ADR-0012](0012-workplace-and-seat-data.md) の決定 3）

## 社内システムへの配信（Webhook）

- 社内システムへの変更の通知（Webhook）の本文は、変わったものの種別（人・組織・拠点）と jin-ji の ID・変更として見せてよい日・取り消しかだけにし、氏名・所属・連絡先などの値は載せない。受け手は自分のトークンで API から取り直す。受け手ごとの項目の上限・公開範囲・将来の予定の秘匿が、通知の経路でも同じに効く
- 受け手に見えない人（公開範囲・退職後の公開期間・入社前）の変更は通知しない。将来の予定の取り消しは、先行提供（有効日の N 日前から予定を見せる設定）を承認された受け手のうち、その予定を通知済みの受け手にだけ知らせる（予定があったことを、知らなかった受け手に明かさない）
- 実装の規則は [概要 §9「Webhook の実装の規則」](../architecture/overview.md#9-社内システム連携下流)

## 帰結

### 良い点

- 漏洩したときの被害が小さく、AI エージェントや LLM に渡すときの心理的・法的な障壁が下がる。AI Ready という目的に合う
- 認可モデルが単純になる（機密区分の段階が要らない）
- 人事パッケージの置き換えや併用にも、取り込みのコネクタを差し替えるだけで対応できる

### 失うもの・注意点

- 氏名と所属だけでも個人情報保護法上の個人情報であることに変わりはない。保存期限・本人からの請求への対応・監査ログは引き続き必要（[概要 §4.5・§4.6](../architecture/overview.md#45-保存期間と消去)）
- 年齢や性別を使う分析（ダイバーシティ指標など）は jin-ji ではできない。必要なら人事パッケージ側で行う
- jin-ji で項目を直しても、正である人事パッケージには反映されない。不整合は「人事パッケージ側で直すべき項目の一覧」（修正依頼）として出力する
- 当日の所在・出社の記録が要る用途（座席予約・入館の管理・勤怠）には jin-ji を使えない。連携先のシステムで扱う
