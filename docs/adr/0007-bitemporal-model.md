# ADR-0007: 二つの時間軸（bitemporal）と、発令を起点にした変更

- ステータス: **承認**
- 日付: 2026-10-18
- 関連: [ADR-0002](0002-data-scope.md)、[ADR-0008](0008-authorization-model.md)（内示の秘匿）、[アーキテクチャ概要 §4.1〜§4.3](../architecture/overview.md#41-二つの時間軸bitemporal)

## 決定

1. **組織・人・所属・発令・拠点のデータは、有効時間と記録時間の二つの時間軸で持つ。**
   - 有効時間（`valid_period daterange`）: 事実として、いつからいつまで有効か
   - 記録時間（`recorded_period tstzrange`）: jin-ji がいつその内容を受け取り、いつ置き換えたか
   - 対象は組織の版・人の属性の版・所属（assignment）・発令・一時停止・拠点の版
2. **訂正は行を上書きしない。** 旧行の `recorded_period` を閉じて新行を追加する。アプリ用の DB ロールには値の列の UPDATE を与えない。唯一の例外は、承認済みの匿名化（保持期限を過ぎた退職者。ADR-0002）で、対象の列を固定した専用の経路で行う。
3. **所属・役職は直接更新せず、取り込んだ発令から版を導出する。** 発令の形を取らないデータ（人事パッケージの現在値のスナップショット等）は、前回との差分から変更を推定し、変更提案として人が確認する。
4. **時点を指定して読める。** REST・MCP・UI の参照は `as_of`（日付）で「ある日時点の組織・所属・上長」を返す。今日より後の時点を指定できるのは人事管理者だけ（内示が見えるため。社内システムへの先行提供は例外として承認を経て設定する。[概要 §9「先行提供の実装の規則」](../architecture/overview.md#先行提供の実装の規則)）。
5. 主務の期間の重複、同じ法人の中での組織コード・拠点コードの重複は、`btree_gist` の排他制約で DB が禁止する。

## 背景

- 人事パッケージからは、遡及発令や訂正が後から届く。有効期間だけでは「その時点で jin-ji が何を知っていたか」が失われる
- 社内システムへの配信（例: 退職者のアカウント停止、Entra ID への同期）が「いつ、どの情報に基づいて行われたか」は、J-SOX の IT 全般統制（アクセス管理）の証跡になる
- 日本企業では 4/1・10/1 などの一斉発令・組織改編が多く、内示（発令日前の異動）を発令日まで秘匿する必要がある。異動を「予定された発令」として持てば、秘匿の線を発令日で引ける

## 検討した選択肢

| 案 | 概要 | 評価 |
| --- | --- | --- |
| A. 現在値だけ + 変更履歴の表 | 本体は上書きし、別表に履歴を残す | 時点指定の参照が履歴の再生になり、内示（未来の版）を表せない |
| B. 有効時間だけ（uni-temporal） | 版に有効期間を持つ | 遡及の訂正で過去の値が書き換わり、配信の根拠を再現できない |
| **C. 二つの時間軸（bitemporal）** | 有効時間と記録時間の両方を持ち、追記だけで変える | 採用。行は増えるが、想定規模（最大 1 万人）では問題にならない |

## 帰結

### 良い点

- 「2026-04-01 時点の所属を、2026-05-10 時点の記録で見る」という問いに答えられ、配信・同期の根拠を後から再現できる
- 内示・組織改編の予定を未来の版として先に取り込み、発令日に効かせられる。秘匿の線は「有効期間の開始」「発令日」で RLS とアプリの両方に引ける
- 変更フィード（[ADR-0011](0011-webhook.md)）は、版の表への追記をトリガーで記録するだけで作れる

### 注意点

- 問い合わせは常に二つの期間の条件を伴う。組織ツリーと関係の判定は、時点ごとのスナップショットをメモリに作って行う（[概要 §5.6](../architecture/overview.md#56-実装上の規則)）
- 記録時間を閉じる更新だけはアプリ用ロールに許す必要があり、トリガーで「値を変えない」ことを守る
- 匿名化は二つの時間軸の唯一の例外で、承認と監査を必須にする
