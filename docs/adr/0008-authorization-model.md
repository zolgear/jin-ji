# ADR-0008: 認可モデル（全社公開を既定に狭める、アプリと RLS の二重の線）

- ステータス: **承認**
- 日付: 2026-10-18
- 関連: [ADR-0002](0002-data-scope.md)、[ADR-0004](0004-authentication.md)、[ADR-0007](0007-bitemporal-model.md)、[アーキテクチャ概要 §5](../architecture/overview.md#5-認可モデル公開範囲)

## 決定

1. **既定は全社公開とし、ポリシーで狭める方向だけに設定する。** 保持するのは全社公開レベルの情報だけなので（ADR-0002）、機密区分の段階は持たない。
2. **公開範囲は、閲覧者から見た対象者との関係（関係スコープ）で表す。** `self`・`same_level(<段のキー>)`・`legal_entity`・`group`・`direct_reports`・`subordinates`・`managers_chain`。課内・部内のような範囲は段を固定せず、法人ごとの段の定義で解決する。兼務者は主務・兼務のすべての所属で判定する（和集合）。
3. **合成は「最も狭いものが勝つ」。** 複数の規則が当てはまれば公開範囲の積を取る。段が法人の定義に無いなど判定できない場合は、広がらない側に倒す。
4. **公開範囲は組織のルールとして決める。** 本人が自分の公開範囲を変える機能は持たない。個人単位の例外（安全上の配慮など）は人事が起案し、狭める方向だけを承認を経て設定する。
5. **利用者（クライアント）ごとに渡す項目の上限を持つ。** 応答は、閲覧者のポリシーとクライアントの上限の両方を満たす項目だけになる。AI エージェントの実効権限は「委任元の人の権限 ∩ スコープ ∩ クライアントの上限」（ADR-0004）。
6. **判定はアプリのポリシーエンジンが唯一の細かい実装で、PostgreSQL の RLS は粗い防波堤とする。** REST・MCP・UI のすべての応答がポリシーエンジンを通る。RLS は、アプリにバグがあっても越えられない線（内示の行・氏名の履歴・取込元の生データ・監査ログなど）だけを引く。
7. **ポリシー・段の定義・ロールの付与・コネクタの項目マッピングの変更は、起案者と別の人の承認を経て反映する**（職務分掌。J-SOX）。

## 背景

- 認可が守るのは、公開範囲の制限（例: 社用携帯は部内のみ）、利用者ごとの項目の最小化、内示の秘匿、管理系の情報（氏名の履歴・監査ログ・取込元の生データ）の 4 つ
- AI による自動の大量取得を想定し、API・MCP・UI のどれから読んでも同じ判定にする必要がある（概要 §1「AI も人も同じ入口・同じ権限判定」）
- 組織の階層は導入先や法人ごとに違う（「本部 > 部 > 課」も「会社 > 事業部 > 部 > 課 > チーム」もある）

## 検討した選択肢

| 案 | 概要 | 評価 |
| --- | --- | --- |
| A. 機密区分（項目に区分を付け、ロールに区分を許す） | 一般的な RBAC | 機微情報を持たないので区分が要らず、関係（課内・上長など）を表せない |
| B. RLS だけで判定する | 判定を DB に寄せる | 関係スコープ・項目単位のマスキングを SQL で書くと複雑で、REST・MCP の応答の形とも結び付かない。閲覧者ごとに結果が変わるのでキャッシュもできない |
| C. アプリだけで判定する | ポリシーエンジンのみ | バグがあれば内示や氏名の履歴が漏れる |
| **D. アプリ（細かい判定）+ RLS（粗い線）** | 二重にする | 採用 |

## 帰結

### 良い点

- 判定の実装が 1 つなので、「API では隠したが MCP では漏れた」という分断が起きない。テーブル駆動のテストで網羅的に確かめられる
- 最悪の漏れ（内示・氏名の履歴・生データ）は DB の線で止まる
- 組織ツリーと関係スコープは、最大 1 万人規模ならメモリ上のスナップショットで判定でき、分散キャッシュは要らない

### 注意点

- 閲覧者の情報はトランザクションの中で `SET LOCAL` してから問い合わせる。アプリ用の DB ロールはテーブルの所有者にしない（所有者は RLS をすり抜けるため）
- RLS の規則を閲覧者個人に依存させる変更をすると、スナップショットのキャッシュの区分を見直す必要がある
- 実装の規則は [概要 §5.6](../architecture/overview.md#56-実装上の規則)
