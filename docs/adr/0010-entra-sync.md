# ADR-0010: Entra ID への反映（スクリプト出力を主、直接反映は既定で無効）

- ステータス: **承認**
- 日付: 2026-10-18
- 関連: [ADR-0001](0001-language-and-runtime.md)（外向き通信）、[ADR-0007](0007-bitemporal-model.md)、[ADR-0008](0008-authorization-model.md)（職務分掌）、[ADR-0014](0014-informal-groups.md)（管理対象のグループの同期）、[アーキテクチャ概要 §8「同期の実装上の規則」](../architecture/overview.md#同期の実装上の規則)

## 決定

1. **Entra ID への反映は「同期計画 + スクリプト」の出力を主とする。** jin-ji は計画（差分・事前条件・優先度）と `Microsoft.Graph` PowerShell のスクリプト一式を出し、管理者がレビューして自分の権限で実行する。実行ログを取り込んで照合する。
2. **直接反映は機能として用意するが、既定では無効とする。** 同じ計画を jin-ji が Graph API で適用する。読み取り用とは別の書き込み用のアプリ（証明書かワークロード ID）を設定し、明示的に有効化したときだけ、管理 CLI からだけ動く（REST API からは起動しない。書き込みの資格情報を API の役割に置かない）。
3. **計画は起案者と別の人事管理者が承認したものだけを使う。** 同期の設定（表示名の形式・部署名の段・除外など）は計画に全文とハッシュを保存し、計画の承認が設定の承認を兼ねる。
4. **計画は業務日付時点の公開側のデータから作る。** 内示・将来の一時停止・退職の予定は反映しない。Entra 側との対応付けは外部 ID の対応だけで行い、同期では名寄せしない。
5. **スクリプト・直接反映とも、更新の前に Entra の現在値を読み、計画時の値かあるべき値でなければその項目をスキップして記録する**（冪等・事前条件）。
6. Graph の呼び出しは HttpClient の最小実装とし、Graph SDK は入れない（ADR-0001）。

## 背景

- Entra ID への書き込みには Microsoft Graph の強い権限（`User.ReadWrite.All` 等）が要る。jin-ji にその権限を常時持たせると、jin-ji の侵害が全社のアカウントの侵害になる
- 退職者のアカウントの無効化・一時停止者のサインイン停止は IT 全般統制の対象で、「誰が、どの情報に基づいて、いつ実行したか」の証跡と職務分掌が要る
- 導入先の情シスは、変更を自分の目で確かめてから流したいことが多い

## 検討した選択肢

| 案 | 評価 |
| --- | --- |
| A. jin-ji が常時 Graph で直接反映する | 運用は楽だが、強い権限を常時持つ。誤りがそのまま全社に流れる |
| B. 差分のレポートだけを出し、作業は手で行う | 安全だが、件数が多いと回らず、実行の証跡と照合ができない |
| **C. 計画 + スクリプトを主、直接反映を任意（既定は無効）** | 採用。jin-ji の常用は読み取りだけで、実行は管理者の権限。必要な導入先だけ直接反映を有効にできる |

## 帰結

- jin-ji が常用する Graph の権限は読み取りだけになる
- スクリプトと直接反映は同じ計画から作るので、テスト・評価は計画の段階でまとめて行える。Graph の呼び出しは差し替えられ、テストはモックで行う（[同期計画の評価](../reports/sync-plan.md)）
- 実テナントでの検証（最小のスコープ、管理者ロールを持つユーザーの扱い、スロットリングなど）は未実施で、[概要 §8](../architecture/overview.md#同期の実装上の規則) の未解決に挙げている
