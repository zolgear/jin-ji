# ADR-0011: 社内システムへの変更の通知（変更フィードと Webhook）

- ステータス: **承認**
- 日付: 2026-10-18
- 関連: [ADR-0002](0002-data-scope.md)（本文に値を載せない）、[ADR-0004](0004-authentication.md)（鍵の保護）、[ADR-0007](0007-bitemporal-model.md)、[ADR-0008](0008-authorization-model.md)、[アーキテクチャ概要 §9](../architecture/overview.md#9-社内システム連携下流)、[Webhook の受け手の実装](../integration/webhook-receiver.md)

## 決定

1. **社内システムへの差分の配信は、変更フィード（pull）を基本とし、Webhook はその「変わった」ことの通知に限る。**
   - 変更フィード `GET /api/v1/changes?since=<cursor>` は、種別（`person` / `org_unit` / `site`）と ID だけを返す。受け手は自分のトークンで API から取り直す
   - Webhook の本文も、種別・ID・見せてよい日・取り消しか・変更フィードのカーソルだけにし、氏名・所属などの値は載せない（ADR-0002）
2. **受け手ごとの項目の上限・公開範囲・将来の予定の秘匿は、通知の経路でも同じに効かせる。** 受け手を閲覧者として変更を集め、受け手に見えない人の変更は通知しない。将来の予定の取り消しは、その予定を通知済みの受け手にだけ知らせる。
3. **受け手は jin-ji が発行するトークンの社内システム（client credentials）だけで、クライアントごとに 1 つ登録する。** 登録・変更・鍵のローテーション・dead の再送は人事管理者の操作として監査する。本文が値を持たず、受け手が読める範囲は Webhook の登録では広がらないので、別人の承認は要求しない。
4. **署名・再送は Standard Webhooks の形に合わせる。** HMAC-SHA256（`webhook-id`・`webhook-timestamp`・`webhook-signature`）、イベント ID を冪等キーにし、指数バックオフで再送して上限で dead にする。届け方は「少なくとも 1 回」。
5. 送信は https だけで、DNS の解決の後に公開でないアドレスを拒否する（CIMD の取得・修正依頼の通知と共通の守り）。標準の HttpClient だけで送り、依存を足さない（ADR-0001）。

## 背景

- 勤怠・承認ワークフローなどの社内システムは、組織改編・異動・退職を速く知りたい。ポーリングだけでは間隔と負荷の兼ね合いになる
- 一方で、通知の本文に値を載せると、受け手ごとの項目の上限・公開範囲・内示の秘匿を通知の経路でもう一度実装することになり、漏れの経路が増える
- 拠点の改称 1 件で数千人分の変更が出ることがある

## 検討した選択肢

| 案 | 評価 |
| --- | --- |
| A. 変更フィードだけ（ポーリング） | 単純だが、即時性が要る受け手には足りない |
| B. 値を載せた Webhook（push） | 受け手は取り直さずに済むが、項目の上限・公開範囲・秘匿を本文の組み立てで二重に守る必要がある。古い値の再送で上書きの順序の問題も出る |
| **C. 変更フィード + ID だけの Webhook（thin event）** | 採用。判定は API の 1 か所のまま。受け手は通知を合図に取り直す |
| D. メッセージキュー（外部の基盤） | 「1 コンテナ + PostgreSQL」の運用の前提（概要 §1）に合わない |

## 帰結

- 受け手の実装は「署名と時刻の検証 → イベント ID で重複を除く → API で取り直す」の形に揃う（[受け手の実装](../integration/webhook-receiver.md)）
- 大量の変更は 1 回の収集で件数が閾値を超えたら要約（`changes.summary`）にし、受け手は変更フィードで追う
- 送信の記録・通知済みの対象・鍵は配信の証跡として消さない。保持期限は運用を見て決める（[概要 §9「Webhook の実装の規則」](../architecture/overview.md#webhook-の実装の規則) の未解決）
