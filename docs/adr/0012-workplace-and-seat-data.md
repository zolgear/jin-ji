# ADR-0012: 建物・階・座席と、人の決まった席・持ち場の扱い

- ステータス: **提案**
- 日付: 2026-10-18
- 関連: [ADR-0002](0002-data-scope.md)（扱うデータの範囲。決定 7）、[建物・フロアモードの仕様と実装方針](../design/building-floor-mode.md)、[アーキテクチャ概要 §4.7・§4.8・§5](../architecture/overview.md)

## 決定（案）

1. **建物・階・簡易フロアマップ（外形・ゾーン・席の置き場所）と、人の決まった席・持ち場（固定席・工場のライン / 持ち場・倉庫のエリア・副の席。有効期間付き）を、全社公開レベルの情報として保持する。** 社内に掲示される座席表と同じ水準とみなす（ADR-0002 の決定 7）。会議室などは配置図の図形としてだけ持つ
2. **座席データの正は、導入先ごとに「jin-ji」か「外部の施設管理システム」のどちらか一方に決める。** 人事パッケージは座席を持たないことが多いため、jin-ji を正にする場合、jin-ji が正になる初めての情報になる。外部を正にした導入先では、jin-ji は取り込むだけにして編集の画面を閉じる（二重管理をしない）
3. **当日の所在・座席予約・フリーアドレスは持たない。** 人事の範疇を超える施設管理で、連携先の範疇である。**所在は保持せず、外部の提供を注入して表示する**（リアルタイムの所在は連携先の範疇）。jin-ji は拡張点（`IPresenceProvider`。既定は「提供なし」）だけを持ち、導入先が登録した提供の今日の所在に、jin-ji の認可（既定の公開範囲は本人と同じ部・ポリシー・個人単位の例外・クライアントの項目の上限。`*` は含めない）を必ず適用して返す。人事管理者を含め、所在だけは全員を一覧できる立場を作らない（人事管理者の全項目の閲覧は所在には効かず、同じ公開範囲で判定する）。所在はキャッシュ・永続化せず、変更フィード・Webhook・監査ログに記録せず、今日の分だけを扱う（仕様 §3.4）
4. **簡易フロアマップは、手で描ける・CSV / JSON で書ける形（整数のミリメートルの座標、多角形・点・既定の机の型）に限る。** CAD・BIM・図面画像・SVG は取り込まない（SVG は表示と書き出しにだけ使う）
5. **将来の席の割り当て（席替えの予定）は、内示と同じ線で人事管理者以外に見せない。**

## 背景

- 3D 表示で拠点を「組織の属性」ではなく「物理的な建物」として扱い、人がどの階・どの席・どの持ち場の人かを把握したいという要望がある（一般社員の同僚探し、総務の座席管理、人事の席替えの計画、AI エージェントへの問い合わせ）
- ADR-0002 は全社公開レベルの情報だけを持つと決めている。決まった席は座席表として社内に公開されることが多い一方、当日の所在は行動の記録で、従業員のモニタリングとして受け取られやすい
- 座席予約・フリーアドレス・会議室の予約・入退館は、施設管理・座席予約のシステムがすでに担う領域で、jin-ji が同じ情報を持つと二重管理になり、人事情報基盤の範囲を超える
- jin-ji は人事情報の正ではない（ADR-0002 の決定 1）。座席のマスタには人事パッケージという正が無く、正の置き場所を決めないと二重管理になる

## 検討した選択肢

| 案 | 概要 | 評価 |
| --- | --- | --- |
| **A. 決まった席・持ち場だけ + 所在は外部の提供の注入** | 建物・階・座席と、有効期間付きの席の割り当て。所在は保持せず、導入先が登録した提供を認可を通して表示する | **採用（案）**。全社公開レベルに収まり、所在の正と保持の責任は連携先に残る |
| B. A に自己申告の座席予約を足す | 本人が日ごとに席を予約する | 不採用。座席予約は施設管理の範疇で、短命のデータ・消去・監査の例外を jin-ji に持ち込む |
| C. 入退館・測位まで取り込む | IC カード・Wi-Fi / BLE の記録から所在を出す | 不採用。本人の操作によらない行動の記録で、監視と受け取られ、勤怠への転用の恐れがある |
| D. フリーアドレスのホームエリア（組織 → エリア）を持つ | 組織ごとの島を持ち、配下が引き継ぐ | 不採用。日々の席の割り振りは施設管理の運用で、人事の決まった席ではない |

## 帰結

### 良い点

- 「〇〇さんの席は？」「3 階の空席は？」に、人・AI エージェントが同じ権限判定で答えられる
- 席の割り当てを有効期間で持つので、タイムマシンで過去の席配置を見られ、席替えの計画を時点で確かめられる
- 所在を保持しないので、消去・監査の例外や監視の懸念を jin-ji に持ち込まない。所在を表示したい導入先は、jin-ji の権限判定を通して連携先の情報を重ねられる

### 注意点

- 席の粒度は人の所在を細かく示すので、項目を「階・エリア（`workplace`）」と「席（`seat`）」に分け、ポリシーで別々に狭められるようにする
- 個人単位の例外で席を隠した人の席は、閲覧者には「使えない席」（保守中・予備と同じ表示）として見せ、例外があることを目立たせない
- 健康・障害を推測させる席の属性（車椅子対応など）は持たない
- 「空席」は割り当ての無い席の意味だけで、予約の空きではない
- 座席データを jin-ji で正として持つ導入先では、jin-ji に新しい編集の責任（総務の運用・承認）が生まれる
- 所在の提供の実装（外部への問い合わせ・認証・失敗時の扱い）は導入先の責任になる。jin-ji の側の認可・保持しない規則は、提供の実装では変えられない

## 未決

- 席（`seat`）の既定の公開範囲（全社か部内か）
- ファシリティ管理者のロールを新設するか、将来の席替えの「誰か」を総務に見せるか（人を伏せた予定の枠）
- 当日の所在（`presence`）の既定の公開範囲（今は本人と同じ部）
