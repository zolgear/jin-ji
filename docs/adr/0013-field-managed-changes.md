# ADR-0013: 現場・IT 部門による組織と人の情報の直接登録と素案（シミュレーション）

- ステータス: **提案**
- 日付: 2026-10-30
- 関連: [ADR-0002](0002-data-scope.md)（決定 1 を見直す）、[ADR-0007](0007-bitemporal-model.md)（決定 3 を見直す）、[ADR-0008](0008-authorization-model.md)、[ADR-0009](0009-agent-writes-hitl.md)（決定 2 を見直す）、[ADR-0011](0011-webhook.md)、[アーキテクチャ概要 §8](../architecture/overview.md#8-取り込み名寄せ同期)

## 決定（案）

1. **公開側を変える入口を 2 つにする。** 取込の変更提案の承認（今のまま）に加え、**現場・IT 部門の直接登録**を設ける。直接登録は承認を経ず、登録した時点で公開側に反映する。人事の承認・ラインの承認ルートは持たない。
2. **領域ごとに「管理元」を導入先が決める。** 領域は次の 5 つ。

   | 領域 | 中身 |
   | --- | --- |
   | `org_structure` | 組織の新設・廃止・名称・略称・上位組織・段・組織長 |
   | `org_site` | 組織の拠点（所在地の移転） |
   | `assignment` | 人の所属・主務/兼務・役職（異動） |
   | `person_site` | 人ごとの拠点・リモートワークの有無 |
   | `person_contact` | 内線・社用携帯 |

   管理元の値は次の 3 つ。

   | 値 | 直接登録 | 取込の差分 |
   | --- | --- | --- |
   | `hr`（既定） | できない | 今のまま変更提案にする |
   | `field` | できる | 提案にせず、「人事パッケージとの差」の一覧に出す |
   | `both` | できる | 提案にする。ただし直接登録した値を変える差分は要確認にする（承認するまで上書きしない） |

   管理元を変えると書き込める人が変わるので、ポリシーと同じく起案者と別の人の承認を経て反映する（ADR-0008 決定 7）。既定は全領域 `hr` とし、設定しない導入先の動きは変わらない。
3. **直接登録できる人と範囲。**

   | 登録者 | 範囲 |
   | --- | --- |
   | 組織長 | その時点で自分が組織長である組織と、その配下 |
   | 組織長が指名した担当（庶務など） | 指名した組織とその配下（指名者の範囲を超えない）。期間付きで、組織に結び付ける（指名者が交代しても残り、後任が取り消せる） |
   | 組織管理者（新設のロール `org_admin`。IT 部門を想定） | 全社 |
   | 人事管理者 | 全社 |

   - **権限を生む変更は、一つ上の範囲を要する。** 組織長の任免・上位組織の付け替え・担当の指名は、その組織の上位の組織の範囲を持つ人（か `org_admin`・人事管理者）だけが登録できる。課長が自分を部長にする、自分の課を別の部へ移して範囲を広げる、といった登録を作らせない。
   - **2 つの組織にまたがる変更は、両方の範囲を要する。** 部をまたぐ異動・上位組織の付け替えは、出し側と受け側の両方の範囲を持つ人ならすぐに反映する。片側の範囲しか持たなければ下書きにし、もう片側の範囲を持つ人の「同意」で反映する（同意は 1 回の操作で、承認ルートではない。期限を過ぎた下書きは消える）。
   - `org_admin` は組織と人の登録・指名・管理元の起案だけを行える。人事管理者と違い、氏名の履歴・取込の作業領域・監査ログは見えない。付与は `hr_corrector` と同じ流儀（自分には付与できない）。
4. **AI エージェントは下書きまでにする。** エージェント（`jinji.propose`）は委任元の名義で直接登録の下書きを作れる。反映するのは委任元の人の確定の操作だけ（ADR-0009 の「公開に至る変更は人が承認する」を保つ）。
5. **直接登録は取込と同じ反映の経路を通る。** 登録は「起案と反映を同じ人が同じトランザクションで行う変更提案」（`origin = field`）として記録する。二つの時間軸・旧値の照合・段の検査・発令の作成（異動・役職の任免）・変更フィード・Webhook・Entra ID の同期計画は、取込の承認と同じに効く。職務分掌の CHECK 制約（起案者 ≠ 承認者）は `origin = field` だけ外す。
6. **時点の規則。**
   - 直接登録の有効日は今日以降だけにする。過去の日付の訂正（遡及）は `org_admin`・人事管理者だけが行える。
   - 有効日が未来の登録は内示と同じに秘匿する。見えるのは登録者・同意者・`org_admin`・人事管理者だけで、対象の本人にも見せない（RLS とアプリ）。
   - 有効日の前なら、登録者か同じ範囲を持つ人が取り消せる（記録期間を閉じる。変更フィードの `withdrawn`）。
7. **承認の代わりに、記録と見える化で守る。**
   - 監査ログに登録・同意・取り消し・指名を残す（拒否・失敗も）。
   - 自分の範囲で誰が何を登録したかの一覧を、範囲を持つ人に見せる。
   - 人事パッケージとの差（管理元が `field`・`both` の領域で、取込の値と jin-ji の値が違うもの）を、人事の担当の作業リストとして出す（修正依頼のレポートと同じ形）。jin-ji から人事パッケージへは書き戻さない。
   - 1 回の登録で変える人数に上限を設ける（既定 50 人）。超える改編は `org_admin`・人事管理者が行う。
8. **反映を目的としない「素案」（シミュレーション）を持つ。** 来期の組織・異動の計画のように、決める前に試す案を、範囲や管理元にかかわらず誰でも作れるようにする。
   - 素案は ADR-0009 の「公開されない作業領域」に置き、公開側を変えない。変更フィード・Webhook・同期計画・承認ルート・時点指定の参照には出さない。AI エージェントも委任元の名義で承認なしに書ける
   - 素案は基準日の公開側の上に変更を重ねたもので、組織図・人の一覧・3D 表示を「素案を適用した姿」で見られ、今の姿との差（人数・異動の一覧）を出せる
   - 素案の中身は作成者の私物とし、見えるのは作成者と、作成者が共有した人だけ。共有された人にも、人の項目は閲覧者自身の公開範囲で投影する（素案を通して見えない項目が見えるようにはしない）。対象の本人に知らせる経路は持たない
   - 素案から反映する経路は 2 つ。範囲を持つ人が素案の一部か全部を直接登録にする（決定 3 の範囲・決定 6 の規則で検査し、作成後に公開側が変わっていれば旧値の照合で止める）か、人事へ渡す一覧（CSV）に書き出す。素案は反映しても残り、どの登録になったかを記録する
   - 素案は保持期限（既定 1 年。最後の更新から）を過ぎたら消す
9. **素案をそのまま申請と提案資料にする。** 組織の計画のたびに組織図を手で起こさず、jin-ji の中で完結させる。
   - 作成者は素案を固定して「申請版」にできる（版番号を持ち、以後は中身を変えない。直すなら次の版）
   - 申請版から提案資料を作る: 今の組織図と素案の組織図（並べて、差を強調）、変更の一覧（異動・新設・廃止・統合・拠点の移転・チームとプロジェクトの変更〔[ADR-0014](0014-informal-groups.md)〕）、組織ごとの人数の増減。画面で表示し、ブラウザの印刷（PDF）・SVG・CSV で出す。新しい依存は足さない（ADR-0001。xlsx は ClosedXML を使う管理 CLI だけ。ADR-0003）
   - jin-ji は承認ワークフローを持たない。申請は社内のワークフロー製品か紙・メールで行い、申請版の URL を添える。承認ルートの候補は既存の承認ルートの API（概要 §9）で出す
   - 作成者は申請版を、承認する人に共有できる。共有された人にも、人の項目は閲覧者自身の公開範囲で投影する
   - 承認された申請版は「承認済み」として記録する（承認日・ワークフロー側の申請番号・記録した人）。記録できるのは、範囲を持つ人か、ワークフロー製品（client credentials。専用のスコープを持つ社内システム）
   - 承認済みの申請版から、操作した人の範囲で直接登録にする（決定 3・6 の検査と旧値の照合）。範囲の外の部分は、`org_admin`・人事管理者が同じ申請版から登録する。どの申請版のどの変更がどの登録になったかを記録する

## 背景

- これまでの設計は、人事パッケージを正とし、公開側を変えるのは人事管理者による取込の承認だけだった（ADR-0002・0007・0009）
- 実際の組織では、異動・組織の改編・拠点の移転は課・部が検討して決め、人事には事後か並行して上げられる。jin-ji は現場で使うものなので、現場の決定が人事パッケージの更新を待たずに反映されないと、組織図・承認ルート・Entra ID が実態から遅れる
- jin-ji の目的は、人事部門が使うシステムと疎結合な組織・人の情報の基盤になることである。人事の承認を必須にすると、jin-ji が人事の業務の流れに依存する
- 異動・組織の変更は、決める前に担当者や各人が素案を作り、来期の計画として比べることが多い。こうした案は反映が目的ではなく、公開側や配信に混ぜてはならない
- 組織の計画の申請では、提案資料のために毎回組織図を手で起こしている。承認された内容も、改めて人の手でシステムに入れ直している
- 一方で、取込と直接登録が同じ値を書くと、次の取込が現場の登録を元に戻す提案を出す。どちらを正とするかを領域ごとに決める必要がある

## 検討した選択肢

| 案 | 概要 | 評価 |
| --- | --- | --- |
| A. 現場の申請 → ラインの承認 → 人事へ引き渡し | 反映は人事パッケージ経由の取込だけ | 不採用。反映が人事の作業と取込の周期に依存し、疎結合にならない |
| B. 人事の承認で jin-ji に直接反映 | 人事管理者が承認者になる | 不採用。人事の承認待ちが残る |
| **C. 範囲を持つ人の直接登録 + 領域ごとの管理元** | 承認なしで反映し、取込との食い違いは管理元で決める | **採用（案）** |
| D. 管理元を持たず、新しい方が勝つ | 取込と登録のうち後に記録した値を採る | 不採用。人事パッケージの古い値の全件取込で、現場の登録が黙って戻る |

## 帰結

### 良い点

- 来期の計画を、公開側を汚さずに組織図・3D 表示の上で試し、決まった分だけ反映できる
- 計画・申請の資料・反映が 1 つの素案でつながり、組織図の作り直しと承認後の入力し直しが無くなる
- 現場の決定がその日のうちに組織図・承認ルート・変更フィード・Entra ID の同期計画に届く
- 人事パッケージを持たない、または組織図を Excel で持つ導入先でも、jin-ji だけで組織と人の情報を回せる
- 既定は今のまま（全領域 `hr`）なので、人事パッケージを正にしたい導入先には影響しない

### 注意点

- jin-ji が、導入先が `field`・`both` にした領域で正になる。ADR-0002 決定 1（正は人事パッケージ、jin-ji は中間パイプ）を「管理元が `hr` の領域では」に限る見直しが要る。ADR-0007 決定 3（所属・役職は取り込んだ発令から）・ADR-0009 決定 2（公開側への入口は取込の承認だけ）も、直接登録を加える形に改める
- 承認がないので、誤った登録はそのまま配信される。取り消し・監査・一覧・人数の上限で、すぐに気付いて戻せるようにする
- 未来日の登録を見られる人が人事管理者の外に広がる。RLS の線（`jinji_viewer_horizon()`）を、登録の関係者に限って開く形に拡張する
- 組織長を範囲の根拠にするので、組織長のデータの誤りがそのまま権限の誤りになる。組織長の任免を一つ上の範囲に限るのはそのため

## 未決

- 「同意」の期限の既定（案: 14 日）
- 人数の上限の既定と、`org_admin` にも上限を設けるか
- 指名の期間の上限（案: 1 年、更新可）
- 有効日を迎えた登録を、対象の本人・関係する組織の組織長に画面内で知らせるか
- 素案を共有する単位（人だけか、組織の範囲を持つ人たちにもか）と、共有された人が素案を編集できるか
- 素案どうしの比較（案 A と案 B）を最初から持つか
- 提案資料の組織図の体裁（導入先の様式に寄せる設定を持つか）と、PDF をサーバーで作るか（今はブラウザの印刷）
- ワークフロー製品から承認の結果を受け取る口（API の呼び出しか、Webhook の受け口か）
- 管理元が `both` の領域で、取込の差分のうち直接登録より前に記録された値をどう扱うか（案: 要確認にして人事管理者が選ぶ）
