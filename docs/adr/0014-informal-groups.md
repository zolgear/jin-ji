# ADR-0014: 規程外の単位（チーム・プロジェクト）をグループとして持つ

- ステータス: **承認**
- 日付: 2026-10-30
- 関連: [ADR-0002](0002-data-scope.md)、[ADR-0007](0007-bitemporal-model.md)、[ADR-0008](0008-authorization-model.md)、[ADR-0009](0009-agent-writes-hitl.md)、[ADR-0010](0010-entra-sync.md)、[ADR-0011](0011-webhook.md)、[ADR-0013](0013-field-managed-changes.md)

## 決定

1. **社内規程に載らず人事システムでも扱わないチーム・プロジェクトなどを、組織（`org_unit`）とは別の「グループ」として持つ。**
   - 種別は固定の少数（`team` チーム・`project` プロジェクト・`committee` 委員会・`other`）
   - 組織のツリーには入れない。上長・承認ルート・段による公開範囲（`same_level`）・人の拠点の既定・Entra ID の部署には影響させない。これらは規程上の組織だけで決める
   - 所管組織（任意で 1 つ）を持てる。組織図・3D 表示では所管組織に添えて表示する
   - 法人の中の段の定義に「チーム」がある導入先の規程上のチームは、今のまま組織として持つ。グループは規程に無い単位だけに使う
2. **メンバーは組織・法人をまたいでよく、1 人が複数のグループに属せる。** 役割は固定の少数（`owner` オーナー・`lead` リーダー・`member` メンバー）とし、自由記述にしない。メンバーには期間を付ける。
3. **管理元は常に jin-ji とする。** 人事パッケージからは取り込まない（持っていないため）。既存の一覧（Excel など）からの初回の取り込みだけ、取込の仕組みで行える。
4. **作成と変更は承認なしで、すぐに反映する。** 頻繁に変わるので、ADR-0013 の直接登録と同じ扱いにする。
   - 誰でもグループを作れる。作成者が最初のオーナーになる
   - 変更できるのは、オーナー・所管組織の範囲を持つ人（ADR-0013 決定 3）・`org_admin`
   - メンバーに加えられた本人は、自分を外せる（アクセス権の管理の対象のグループを除く。決定 6）
   - 二つの時間軸（ADR-0007）で持つ。アクセス権の根拠になるので、「いつ誰が誰を加えたか」と「いつからいつまでメンバーだったか」を後から再現できるようにする
   - ADR-0013 の素案と申請版に、グループの変更も入れられる
5. **公開範囲。**
   - 既定は全社公開（名前・種別・所管組織・メンバーと役割）
   - グループごとに「メンバーだけ」を選べる（社外秘のプロジェクトなど）。存在が見えるのはメンバー・オーナー・`org_admin`・人事管理者だけになる（RLS とアプリ）
   - 人の項目としての「所属するグループ」（`groups`）を項目カタログに足し、他の項目と同じくポリシーとクライアントの項目上限で狭められるようにする
6. **アクセス権の管理に使うのは、`org_admin` が「管理対象」にしたグループだけにする。**
   - 管理対象のグループは、関係スコープ `same_group`（同じグループのメンバー）としてポリシーに書け、Entra ID のセキュリティグループ・Microsoft 365 グループへの同期の対象にできる
   - 管理対象のグループのメンバーの変更は、オーナー・所管組織の範囲を持つ人・`org_admin` だけが行える（自分を加えて公開範囲や権限を広げられないようにする）。オーナーの指名は `org_admin` か所管組織の範囲を持つ人だけ
   - 誰でも作れるグループのままでは、関係スコープにも同期にも使えない
7. **配信と AI エージェント。**
   - 変更フィード・Webhook の種別に `group` を足す（本文は種別と ID だけ。ADR-0011）
   - REST・MCP でグループの一覧・詳細・人の所属するグループを引ける。認可は人の参照と同じ判定
   - グループの変更は公開される情報（アクセス権に効く）なので、AI エージェントは下書きまでにする（ADR-0009。ADR-0013 決定 4 と同じ）
8. **Entra ID への同期は ADR-0010 と同じ形にする。** 管理対象のグループのメンバーの差分を、実行計画とスクリプトにして出す。直接反映は既定で無効。詳細は ADR-0010 の見直しで決める。

## 背景

- 現場とアクセス権の管理では、規程上の組織よりも、チーム・プロジェクトといった単位が重要なことが多い（共有フォルダ・チャット・業務システムの権限、連絡の宛先）
- こうした単位は規程・人事システムに載らず、頻繁に変わる。今は Entra ID のグループや表計算で個別に管理され、異動や退職のときに外し忘れが起きる
- jin-ji は在籍・所属を持っているので、グループを持てば、退職・異動に合わせたメンバーの見直しと、アクセス権の根拠の記録を同じ場所でできる

## 検討した選択肢

| 案 | 概要 | 評価 |
| --- | --- | --- |
| A. 組織（`org_unit`）の段にチーム・プロジェクトを足す | 段の無い組織として持つ | 不採用。組織は木で、主務の所属・上長・承認ルートの根拠になる。組織をまたぐメンバーや、1 人の複数の所属を表せない |
| **B. 組織と別のグループを持つ** | 多対多のメンバー。組織の判定には効かせない | **採用** |
| C. 持たずに Entra ID のグループに任せる | jin-ji は関与しない | 不採用。異動・退職とのつながりが切れ、規程外の単位を組織図・AI エージェントから引けない |

## 帰結

### 良い点

- 規程上の組織とチーム・プロジェクトを同じ組織図・同じ API・同じ認可で扱える
- 退職・異動のときに、その人が属するグループ（とアクセス権）を一覧でき、外し忘れに気付ける
- アクセス権に使うグループを管理対象に限るので、誰でも作れる柔軟さと、権限の管理の厳しさを両立できる

### 注意点

- 誰でも作れて人を加えられるので、望まないグループに加えられることがある。監査ログ・本人による脱退・`org_admin` による削除で対処する
- 「メンバーだけ」のグループの存在は、全社公開のレベルを超える情報になり得る。ADR-0002 の「全社公開レベルの情報だけを持つ」との整合は、メンバーだけに見せる業務上の情報（人の機微情報ではない）として扱う
- 関係スコープ `same_group` を足すと、ポリシーの判定がグループの変更に依存する。スナップショット（ADR-0008）にグループを含め、変更で捨てる

## 未決

- 退職・異動のときに、グループのメンバーを自動で外すか（案: 退職は自動で外す。異動は所管組織の範囲を持つ人とオーナーに見直しの一覧を出す）
- オーナーがいなくなったグループの扱い（案: 所管組織の組織長、無ければ `org_admin` に引き継ぐ）
- 期限付きのプロジェクトの終了日を過ぎたグループを自動で閉じるか
- グループの入れ子（プロジェクトの下のサブチーム）を許すか
