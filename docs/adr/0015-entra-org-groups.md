# ADR-0015: 組織に対応する Entra ID のグループの作成と同期

- ステータス: **提案**
- 日付: 2026-11-12
- 関連: [ADR-0008](0008-authorization-model.md)（職務分掌）、[ADR-0010](0010-entra-sync.md)（計画 + スクリプトを主にする）、[ADR-0014](0014-informal-groups.md)（管理対象のグループの同期）

## 決定

1. **規程上の組織（`org_unit`）ごとに Entra ID のグループを作り、メンバーを jin-ji の所属に合わせる。** 反映は ADR-0010 と同じ形（計画 → 別の人事管理者の承認 → 反映 → 実行結果の照合）にする。反映の手段は決定 8。
   - グループの種類は設定で選ぶ: セキュリティグループ（既定）か Microsoft 365 グループ。Microsoft 365 グループでは、設定で Teams のチームも作れる（チームにはオーナーが要るので、組織長をオーナーにする。組織長に Entra のアカウントの対応が無ければ、チームは作らずに計画に出す）
   - 種類は作った後で変えられない。設定と違う種類のグループは変更せず、計画に出す
   - 計画はユーザーの同期とは別の種類（同期先 `entra_id_groups`）にする。入力（Entra のグループの一覧）と実行の頻度が違い、承認も別に行えるようにするため。作業領域の表（`sync_plan` ほか）と承認・古い計画（stale）の扱いは共有する
   - 組織のツリーを Entra の部署（`department`）に効かせない方針（ADR-0014 決定 1）は変えない。グループは部署の属性とは別のもの
2. **グループの名前には接頭辞を付け、既存のグループと衝突しないようにする。**
   - 表示名は「接頭辞 + 形式」（既定は組織の名前。法人名・組織コードを差し込める）。`mailNickname` は「ASCII の接頭辞 + 法人コード + 組織コード」
   - 接頭辞は同期の設定で指定する（計画に全文を保存するので、計画の承認が設定の承認を兼ねる。ADR-0010 決定 3）
3. **jin-ji が扱うのは、jin-ji の印の付いたグループだけにする。**
   - 作るときに、説明（`description`）に組織の ID を含む印（`jinji-org:<組織の ID>`）を書く。以後の計画は、この印でグループと組織を対応付ける（名前では対応付けない。組織の改称でグループを作り直さない）
   - 印の無いグループは、名前や `mailNickname` が同じでも変更しない。同じ名前のグループが既にあるときは、作成を計画に入れず「名前の衝突」として出す（接頭辞を変えるか、管理者がそのグループの説明に印を書いて引き継ぐ）
4. **メンバーは「その組織と配下の組織で働く人」を直接入れる（既定）。**
   - 主務に加えて、兼務・出向受入の人も入れる（既定）。設定で「直属だけ」「主務だけ」にできる
   - Entra のアカウントとの対応は、ユーザーの同期と同じ外部 ID の対応だけを使う（名寄せしない）。対応の無い人は入れられないので、参考として出す
   - 入れ子のグループ（配下の組織のグループをメンバーにする）は使わない。入れ子を解釈しないアプリで権限が効かないため
5. **外すのは、jin-ji の人に対応付いたメンバーだけにする（既定）。** 異動・退職で対象から外れた人をグループから外す。管理者が手で加えたアカウント（サービスアカウントなど、jin-ji の人に対応付かないもの）は外さず、参考として出す。設定で除外したユーザーは加えも外しもしない。
6. **グループは削除しない（物理削除をしない）。組織の変更は、グループの更新として反映する。**
   - 組織の改称・法人名の変更: 表示名を更新する（印で対応付けているので、作り直さない）
   - 組織の廃止: グループは残し、表示名に廃止の印（設定。既定は「【廃止】」）を付け、説明に廃止を書く。**メンバーは残す**（引き継ぎ先のグループに権限を付け替えるまで、権限を持ったままにする。メンバーを外して空のグループだけを残しても意味が無い）。外すのは退職した人だけ
   - 削除は、それに結び付いた権限・Teams の会話を一度に失わせるので、管理者が確かめて行う
7. **反映は ADR-0010 決定 5 と同じく、変更の前に現在の状態を読む。** 既にメンバーなら追加を、既にメンバーでなければ削除をスキップして記録する（冪等）。グループの作成は、同じ印のグループが既にあれば作らない。
8. **反映は Graph API での直接反映で行う。** 承認済みの計画を、jin-ji が Graph API で適用する（グループの作成・更新、メンバーとオーナーの追加・削除、チームの作成）。スクリプト出力（ADR-0010 決定 1 の主の手段）は、グループの計画では後から足す。
   - 有効化・資格情報・起動の経路は ADR-0010 決定 2 のまま（既定は無効。書き込み用のアプリを明示的に設定したときだけ、管理 CLI からだけ動く）
   - 計画の入力（Entra のグループとメンバーの一覧）も、ファイルに加えて Graph API から読めるようにする

## 背景

- 共有フォルダ・チャット・業務システムの権限は、組織の単位のグループに与えることが多い。今は情シスが手で作り、異動・退職のときの外し忘れが起きる
- jin-ji は業務日付時点の所属を持っているので、組織の単位のグループのメンバーを決められる
- 導入先の Entra ID には既にグループがある。名前だけで対応付けると、別の用途の同名のグループを書き換えるおそれがある

## 検討した選択肢

| 案 | 評価 |
| --- | --- |
| A. 名前（接頭辞 + 組織名）でグループを対応付ける | 不採用。組織の改称で対応が切れる。同名の既存のグループを誤って書き換える |
| **B. 接頭辞で見分けやすくし、対応付けは説明に書いた印で行う** | 採用。接頭辞は人の目のため、印は機械の対応付けのため。印の無いグループには触らない |
| C. グループのオブジェクト ID を jin-ji の表に持つ | 不採用（今は）。スクリプトで作ったグループの ID を jin-ji に戻す手順が要る。印なら次の計画の入力から分かる |
| E. 廃止された組織のグループを削除する | 不採用。権限と Teams の会話を一度に失う。更新（廃止の印）に留める |
| D. 動的グループ（部署の属性の規則でメンバーを決める） | 不採用。Entra ID の上位のライセンスが要る。配下を含む・兼務を含むを規則で書けない |

## 帰結

- ユーザーの同期と同じ承認・証跡（起案者 ≠ 承認者、実行ログの照合）で、グループのメンバーの変更を残せる
- 計画の項目はメンバーの追加・削除 1 件ごとに持つ（誰をいつ外したかを照合できる）。配下を含むので、最初の計画は項目が多くなる（人数 × 組織の深さ）
- 必要な Graph の権限は、読み取りに `Group.Read.All`・`GroupMember.Read.All`、直接反映に `Group.ReadWrite.All`・`User.Read.All`（チームを作るなら `Team.Create`）
- グループの計画では、スクリプト出力が無い間、反映に書き込み用のアプリの設定（ADR-0010 決定 2）が要る

## 未決

- Microsoft 365 グループのメールアドレス（`mailNickname`）が既存のアドレスと衝突したときの扱い（今は Graph のエラーを項目の失敗として記録する）
- チームの設定（チャネル・ゲストの可否など）は扱わない。作るだけにする
- 対象の組織を段で絞る設定の既定（今はすべての組織）
- ADR-0014 の管理対象のグループの同期を、同じ仕組みに載せる（印は `jinji-group:<グループの ID>` を想定）
- グループの計画のスクリプト出力（`Microsoft.Graph` PowerShell）
- 実テナントでの検証（スロットリング、メンバーの多いグループ、チームの作成の応答）
